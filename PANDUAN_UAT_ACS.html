Pengujian Penerimaan Pengguna (UAT)

Panduan UAT ACS

Skenario uji, checklist persiapan, lembar hasil, dan kriteria lulus — Tim Operasional & Tim Network

Hari pelaksanaan: Rabu, 21 Oktober 2026  ·  Versi dokumen: 1.2 (disusun 16 Oktober 2026; diperbarui 17 Oktober setelah laporan SaaS, impersonate, paket, portal pelanggan, vendor generik)  ·  Peserta: Tim Operasional (NOC), Tim Network (OLT/jaringan), Tim Pengembang
Tujuan UAT

Memastikan ACS bisa dipakai tim operasional dan network untuk pekerjaan sehari-hari pada ONT sungguhan: ONT muncul di ACS, bisa dibaca, diubah konfigurasinya (WiFi dll.), di-reboot, dan semua aksi tercatat. Sistem ini belum pernah menerima Inform dari ONT fisik — validasi sebelumnya memakai simulator (16 skenario e2e lulus). UAT ini adalah bukti pertama di dunia nyata, jadi temuan itu diharapkan dan berharga.

Ingat pembagian tanggung jawab

ACS mengonfigurasi sisi ONT, bukan OLT. Tim Network tetap mengerjakan sisi OLT (registrasi ONT, VLAN, jalur manajemen); ACS mengatur konfigurasi di dalam ONT lewat TR-069. Penjelasan bergambar: Buku Panduan ACS, Bab 1.

2 Peta tugas: siapa mengerjakan apa, kapan

Tiga tim, satu tujuan. Ringkasannya: Tim IT menyiapkan sistem ACS (server, aplikasi, akun, data awal) dan menjaganya tetap hidup saat uji; Tim Network menyiapkan jalur jaringan dan ONT uji, lalu menyalakan ONT agar terhubung ke ACS; Tim Operasional mengoperasikan ACS lewat Console seperti pekerjaan harian dan menilai apakah alurnya layak dipakai. Detail langkah per tim ada di §3 (IT), §4 (Network), §5 (Operasional).

2.3 Go/No-Go persiapan (Selasa 20 Okt, sore)

IT memimpin cek singkat 15 menit bersama ketua tiap tim. Semua harus ✔ agar Rabu berjalan; bila ada yang belum, putuskan: tunda bagian tersebut atau geser jadwal.

  • ☐ Console terbuka & login berhasil dari PC Ops dan PC Network.
  • ☐ curl POST kosong ke ACS URL dari segmen ONT menghasilkan 204.
  • ☐ Minimal 1 ONT uji sudah dikonfigurasi dengan ACS URL + kredensial dan siap dinyalakan.
  • ☐ Backup database sebelum UAT sudah ada dan tercatat (§12.1).
  • ☐ Akun semua penguji bekerja; tenant pilot & kredensial CWMP sudah di tangan Network.
  • ☐ Versi aplikasi dibekukan (catat commit di §12.1).

3 Tim IT — apa yang harus dikerjakan IT

Peran Anda

Menyediakan sistem yang hidup, terjangkau, aman, dan bisa dipantau, lalu mendampingi hari-H (membaca log, membantu triase) tanpa mengubah sistem di tengah uji. Anda bukan penguji utama; keberhasilan UAT diukur oleh Operasional dan Network.

3.1 Keputusan awal (Jumat 16 Okt)

  1. Pilih host. Disarankan server Linux dengan IP statis, terjangkau dari jaringan Ops (Console) dan jaringan manajemen ONT (CWMP).
    Hati-hati: Docker Desktop di Windows

    Di Docker Desktop (Windows) alamat sumber koneksi umumnya tersamarkan menjadi alamat internal Docker (pada mesin pengembangan, request dari host terlihat sebagai 172.21.0.1; pastikan dengan langkah §3.5 butir 4). Bila itu terjadi: (a) ACS tidak otomatis menyimpan Connection Request URL (sistem mensyaratkan host URL = IP sumber Inform, anti-SSRF) → tombol Connection Req mati sampai URL diisi manual lewat Edit perangkat; (b) batas 5 req/dtk dihitung bersama untuk semua ONT. Di Docker native Linux, IP sumber asli terjaga. Bila terpaksa Windows: isi Connection Request URL manual (mis. http://<IP-ONT>:7547/) dan nyalakan ONT bergantian.

  2. Tentukan skema ACS URL. acsd sendiri melayani HTTP polos. LAN uji tertutup: HTTP boleh. Tanyakan Network sebelum Senin apakah firmware ONT uji mewajibkan https://. Bila ya dan Anda punya nama domain publik (DNS menunjuk ke server, port 80/443 terbuka), pakai overlay siap-pakai docker-compose.tls.yml + deploy/Caddyfile (Caddy, sertifikat Let's Encrypt otomatis; langkah di RUNBOOK.md §F) — sudah diuji fungsional (API, WebSocket, /cwmp, Console) tetapi belum dengan ONT fisik. Tanpa domain publik, sertifikat internal Caddy tidak dipercaya ONT → tetap HTTP di LAN.
  3. Rencana port (buka hanya yang perlu; jangan expose DB/Redis/MinIO/Grafana ke jaringan uji):
Port (default compose)FungsiArah & siapa

3.2 Menyiapkan server (Senin 19 Okt)

  1. Ambil kode & catat versi. 
    git clone https://github.com/rmdhfz/acs.git && cd acs
git checkout dev && git pull
git log -1 --oneline      # catat commit ini di §12.1
  2. Buat .env dari .env.example (cp .env.example .env) dan isi nilai baru, jangan memakai nilai dari lingkungan pengembangan: 
    openssl rand -base64 48   # → ACS_JWT_SECRET
openssl rand -base64 32   # → ACS_CREDENTIAL_ENC_KEY
# juga: ACS_DB_ROOT_PASSWORD, ACS_DB_PASSWORD, ACS_MINIO_ACCESS_KEY, ACS_MINIO_SECRET_KEY (acak, kuat)
ACS_PUBLIC_URL=http://<IP-server>:5173            # alamat Console; dipakai di tautan email
ACS_CORS_ALLOW_ORIGINS=http://<IP-server>:5173    # origin Console, tanpa slash akhir
ACS_REDIS_PASSWORD=<acak, kuat>                  # disarankan; kosong = Redis tanpa auth
ACS_TRUSTED_PROXIES=                           # isi IP/CIDR reverse proxy bila ada; kosong = X-Forwarded-For diabaikan
ACS_LOG_RETENTION_DAYS=90                      # retensi tabel log (hari); 0 = nonaktif
# email: ACS_SMTP_HOST / PORT / USERNAME / PASSWORD / FROM  (App Password BARU, bukan yang lama)
    Penting

    ACS_CREDENTIAL_ENC_KEY mengenkripsi kredensial tersimpan (secret CWMP tenant, kredensial Connection Request). Jangan diganti setelah data terisi — data lama jadi tak terbaca. Untuk UAT, buat sekali di database baru lalu simpan di pengelola rahasia. .env jangan di-commit atau dikirim lewat chat.

  3. Catatan port: database, Redis, konsol MinIO, Prometheus, Grafana, dan Alertmanager hanya terbuka di 127.0.0.1 server (sengaja). Yang terbuka ke jaringan: REST (18080), CWMP (17547), dan MinIO API (19000, hanya perlu bila firmware diunduh CPE — tidak dipakai pada UAT ini; boleh diblok firewall). Untuk melihat Grafana dari PC lain gunakan SSH tunnel.
  4. Jalankan stack. 
    docker compose up -d --build
docker compose ps                    # migrate: Exited (0); mariadb, redis, minio: healthy; acsd: Up
docker compose logs --tail 50 acsd   # tidak ada error
    Jika gambar MinIO gagal diunduh, laporkan — firmware tidak diuji pada UAT ini, tetapi acsd menunggu MinIO sehat.
  5. Buat Superadmin pertama (akun Anda sendiri; password kuat, bukan kata sederhana): 
    docker compose exec acsd /app/seed-admin -username <user> -password '<password-kuat>' -email <email-anda> -fullname "<Nama>"
  6. Firewall — izinkan inbound dari subnet uji ke tiga port (§3.1) saja. 
    # Linux (contoh ufw)
sudo ufw allow from <subnet-uji> to any port 5173,18080,17547 proto tcp
# Windows (PowerShell, Administrator)
New-NetFirewallRule -DisplayName "ACS UAT" -Direction Inbound -Protocol TCP -LocalPort 5173,18080,17547 -Action Allow -RemoteAddress <subnet-uji>

3.3 Menyiapkan Console web

Console belum berupa container; ia dibangun sekali dengan alamat API server (bukan localhost — peramban penguji berada di komputer lain) lalu disajikan sebagai berkas statis. Cara ini sudah diuji (login lewat build + vite preview berhasil).

cd frontend && npm ci
# Linux/macOS/Git-Bash
VITE_API_BASE_URL=http://<IP-server>:18080/api/v1 npm run build
# Windows PowerShell:   $env:VITE_API_BASE_URL="http://<IP-server>:18080/api/v1"; npm run build
npx vite preview --host 0.0.0.0 --port 5173     # biarkan berjalan (tmux/screen/service)

Beranda publik (landing page SEO) ikut terbangun pada perintah yang sama: isi juga VITE_SITE_URL (URL publik, tanpa slash akhir) dan opsional VITE_CONTACT_EMAIL; lihat frontend/.env.example. Pengunjung anonim yang membuka alamat dasar melihat beranda; tombol Masuk menuju /login.

Uji dari PC lain: buka http://<IP-server>:5173/login, login. Bila halaman terbuka tetapi login gagal dengan galat jaringan/CORS → periksa ACS_CORS_ALLOW_ORIGINS (harus persis sama dengan alamat di peramban) dan firewall port 18080. Catatan: vite preview bukan server produksi — cukup untuk UAT di LAN tertutup.

3.4 Menyiapkan data awal di ACS

Login sebagai Superadmin di Console:

  1. Tenant pilot: Administrasi → Tenants → Tambah (mis. kode UAT). Lalu tombol Kredensial CWMP: set username (mis. uat-pilot) dan password acak yang kuat. Catat — ini yang diisi ke ONT. Kirim ke Network lewat kanal aman (§2.2).
  2. Akun penguji (Administrasi → Users → Tambah, atau Impor CSV; pilih tenant pilot). Saran: Ops — 1 ADMIN + 2 NOC; Network — 1–2 NOC (bisa Connection Request & edit kredensial CR); 1 VIEWER (uji O16). Email harus alamat nyata & unik. Beri password sementara lewat kanal aman; minta ganti di Profil → Ganti password saat login pertama (atau biarkan kosong dan minta mereka memakai Lupa password).
  3. Katalog vendor (Katalog Vendor): dari daftar ONT Network, pastikan vendor ada dan OUI ONT terdaftar (OUI pada Inform = kode produsen, sering sama dengan 3 byte pertama MAC tetapi tidak selalu). Bila ProductClass model diketahui, daftarkan model (tab Model). OUI yang belum ada tidak menghalangi uji: perangkat muncul "vendor belum diketahui" dan sembuh sendiri setelah OUI ditambahkan.
  4. (Opsional) Pra-registrasi ONT dari daftar Network lewat Perangkat → Impor (contoh CSV di §5.1) — memudahkan pengecekan serial↔tenant.
  5. (Opsional) Penerima webhook uji bila O20 akan dicoba.
  6. Interval polling redaman optik: bawaan 360 menit (ACS_OPTICAL_POLL_MINUTES). Agar N10 terlihat saat UAT, set ACS_OPTICAL_POLL_MINUTES=15 (minimum) di .env lalu docker compose up -d acsd. ACS membaca optik setelah Inform bila data terakhir lebih tua dari interval itu, hanya untuk vendor/model yang punya mapping optical.* di Katalog.

3.5 Uji asap & gladi (Senin–Selasa)

  1. Dari PC lain (bukan server): login Console berhasil; "Lupa password" mengirim email ke alamat nyata (cek spam).
  2. Dari segmen jaringan ONT (minta bantuan Network): curl -i -X POST http://<ACS>:17547/cwmp → 204.
  3. Cek kesehatan: curl http://<ACS>:18080/readyz → {"status":"ready","checks":{"database":"ok","redis":"ok"}} (503 + "database":"down" bila DB mati; /healthz selalu 200 selama proses hidup). docker compose ps menampilkan acsd healthy.
  4. Gladi dengan simulator dari mesin di segmen ONT: go build -o cpesim ./cmd/cpesim lalu 
    ./cpesim -acs http://<ACS>:17547/cwmp -user <user-cwmp> -pass <pass-cwmp> -vendor zte -serial GLADI-001 -events "0 BOOTSTRAP" -v
    Harapan: inform=200 dan GLADI-001 muncul di Console (tenant pilot). Detail & Connection Request: PENGUJIAN_LAPANGAN.md §3a.
  5. Periksa IP sumber: di docker compose logs acsd, baris permintaan /cwmp harus menunjukkan remote_ip = IP mesin simulator (bukan 172.x). Jika bukan → ikuti catatan Docker Desktop (§3.1).
  6. Hapus perangkat gladi (GLADI-001) agar daftar bersih.
  7. Tutup dengan backup (§13) dan catat nama berkasnya di §12.1.

3.7 Tugas IT pada hari-H

  • Sebelum mulai (08.30): docker compose ps semua sehat; backup tercatat; Console terbuka; jendela log siap; kontak Network & Ops tersedia.
  • Selama uji: amati log; bantu Network membaca penyebab ONT tak muncul (tabel §3.6); catat jam kejadian setiap gejala aneh; jangan deploy ulang atau mengubah konfigurasi kecuali S1 yang menghentikan semuanya (catat jam & alasan).
  • Permintaan data katalog: bila ONT muncul "vendor belum diketahui" atau butuh model/mapping baru, tambahkan lewat Katalog Vendor/Impor (operasi data, bukan rilis).
  • Triase: sebelum 13.45 kumpulkan lembar hasil Network & Ops, tetapkan tingkat keparahan bersama (§11).

3.8 Setelah UAT (Kamis 22 Okt)

  1. Backup database sesudah uji (§13) & ekspor Audit Trail (Console → Audit Trail → Ekspor) sebagai arsip.
  2. Buat tiket untuk semua temuan (pakai templat §12.3) dan jadikan daftar perbaikan berprioritas; perbarui katalog dari path/OUI/model yang ditemukan.
  3. Bersihkan: hapus/nonaktifkan akun uji yang tak diperlukan, cabut API token bila ada, putar kembali password CWMP tenant pilot bila ONT uji akan dikembalikan ke penggunaan lain.
  4. Siapkan keputusan lanjutan dari hasil: TLS untuk CWMP pada ONT fisik, jadwal pilot terbatas, dan OLT Controller.

4 Tim Network — apa yang harus dikerjakan NET

Peran Anda

Memastikan ONT uji bisa menjangkau ACS dan sebaliknya, lalu menyalakan ONT dan menguji Bagian A. ACS tidak mengubah OLT — Anda tidak perlu mengubah konfigurasi OLT selama uji selain yang biasa dilakukan untuk authorize ONT dan menyediakan jalur manajemen.

4.1 Yang Anda butuhkan dari Tim IT

Minta (§2.2): ACS URL lengkap (skema, IP/nama, port, path /cwmp), username & password CWMP tenant pilot, IP server ACS, kontak IT hari-H. Bila ONT uji mewajibkan https://, kabari IT sekarang.

4.2 Persiapan (Senin–Selasa)

  1. Pilih 2–3 ONT uji — idealnya ≥ 2 vendor berbeda, boleh diatur ulang/gagal, bukan milik pelanggan aktif. Catat vendor, model, firmware, serial, MAC, mode (router/bridge), lalu serahkan ke IT (§12.2). Pastikan agen TR-069 tersedia & aktif (ONT mode bridge/SFU sederhana bisa tanpa agen — pilih yang punya).
  2. Buka jalur dua arah pada VLAN/WAN manajemen:
    • ONT → ACS: rute ke IP server ACS dan TCP ke port CWMP (mis. 17547) diizinkan firewall/ACL.
    • ACS → ONT: TCP ke port Connection Request ONT (umumnya 7547; lihat nilai yang dilaporkan ONT) diizinkan. Ini arah yang paling sering lupa dibuka.
    • Catat bila ada NAT/CGNAT di antara ONT dan ACS, serta IP sumber yang akan terlihat ACS.
  3. Uji jangkauan dari segmen ONT (bukan dari server ACS): 
    curl -i -X POST http://<ACS>:<port>/cwmp                       # harus HTTP 204
# PowerShell: (Invoke-WebRequest -Method Post -UseBasicParsing http://<ACS>:<port>/cwmp).StatusCode
  4. Pastikan ONT sudah authorize di OLT dan memperoleh IP manajemen (dari OLT/DHCP). Bila GUI ONT menyediakan ping/diagnostik, uji ping ke IP ACS.
  5. Isi pengaturan TR-069 di ONT (menu "TR-069 / ACS / Remote Management" — lokasi berbeda tiap vendor; lihat manual ONT). Alternatif memberi tahu URL ACS lewat OMCI atau DHCP Option 43 boleh dipakai bila sudah siap; mengisi manual paling cepat untuk UAT:
    Field di ONTIsi
    ACS URLdari IT, mis. http://<IP-ACS>:17547/cwmp
    ACS Username / PasswordKredensial CWMP tenant pilot (dari IT)
    Periodic InformAktif; interval 300 detik
    Connection Request Username / PasswordIsi sendiri (catat) — lalu beri tahu Ops/IT agar dimasukkan ke ACS (kasus N6)
  6. Siapkan ONT "baru" untuk G1: 1 ONT yang belum pernah terdaftar di ACS; kredensial ACS sudah diisi, belum dinyalakan/belum authorize di OLT.
  7. Serahkan daftar ONT uji (§12.2) & username/password Connection Request ke IT pada Senin–Selasa.

4.3 Hari-H

  1. Urutan: N1 (jangkauan) → nyalakan ONT pertama → N2–N3 → N6 (Connection Request) → N4, N5, N7–N10. Untuk beberapa ONT: bergantian ±10 detik.
  2. Tiap kasus: Network menjalankan langkah di ONT/OLT; Ops mengamati hasil di Console; IT membaca log. Setelah ONT dinyalakan, tunggu sampai ±2 menit sebelum menyimpulkan gagal.
  3. Bukti yang diambil bila gagal: tangkapan layar halaman TR-069 ONT (status/hasil terakhir koneksi), hasil curl, status ONT di sistem OLT, jam kejadian.
  4. Selama G1: Network authorize & menyalakan ONT "baru", mengonfirmasi IP manajemen, lalu menyerahkan pantauan ke Ops.
  5. Bila ONT tak muncul di ACS: ikuti tabel gejala (§13) — periksa urut: IP manajemen → rute/firewall → ACS URL & port → username/password → rate limit.

4.4 Setelah UAT

  • Serahkan lembar hasil Bagian A (§7) dan temuan jaringan.
  • Kembalikan ONT uji ke kondisi semula (hapus/ubah ACS URL uji bila perlu).
  • Laporkan path parameter/ProductClass/OUI yang berbeda dari dugaan, dan hasil perbandingan redaman optik (N10) bila dicoba.

5 Tim Operasional — apa yang harus dikerjakan OPS

Peran Anda

Memakai ACS seperti pekerjaan harian dan menilai: apakah alurnya jelas, benar, dan layak dipakai. Anda tidak perlu paham teknis jaringan; yang penting mencatat apa yang dilakukan, apa yang terjadi, dan apa yang membingungkan.

5.1 Persiapan (Jumat–Selasa)

  1. Kirim ke IT (Jumat 16 Okt): nama, email aktif, peran (ADMIN / NOC / VIEWER) tiap penguji. Disarankan 1 ADMIN, 2 NOC, 1 VIEWER agar hak akses (O16) bisa diuji.
  2. Login uji dari PC Anda setelah akun diterima (Senin): buka Console, login dengan email + password, ganti password di Profil → Ganti password, pastikan email dari sistem masuk (cek spam). Bila tak bisa login → hubungi IT hari itu juga.
  3. Baca Buku Panduan ACS Bab 1 (ACS di OLT atau ONT?), Bab 7 (perangkat), 8 (impor/ekspor), 9 (task), 10 (provisioning), 11 (preset).
  4. Siapkan data uji (milik uji, bukan pelanggan): nama SSID uji (mis. UAT-Rabu-01, UAT-Rabu-02), password WiFi uji (≥ 8 karakter), 2 serial perangkat buatan sendiri untuk O5/O7 (mis. UAT-TEST-001), nama tag, nama profil & preset uji, dan file CSV impor berikut (simpan sebagai impor-uat.csv):

  5. Bagi peran per sesi: Penguji (memegang keyboard), Pencatat (mengisi lembar hasil & menangkap layar), Pengamat ONT (memeriksa fisik: SSID di HP, lampu ONT). Siapkan HP untuk melihat SSID.

5.2 Hari-H

  1. 09.20–10.30: kerjakan O1–O4 (login, lupa password, profil, dashboard) sementara Network menyalakan ONT pertama.
  2. Begitu ONT pertama muncul di Perangkat (diberi tahu Network): kerjakan O5–O12 berurutan pada ONT itu. Cari ONT lewat kolom Cari (serial) atau Ctrl+K.
  3. Setelah setiap kasus: centang hasil di lembar (☐ Lulus / ☐ Gagal), tulis catatan singkat. Jangan lanjut ke langkah berikutnya pada kasus yang gagal; catat & pindah kasus lain.
  4. Bila gagal: tangkap layar (termasuk jam), isi templat temuan (§12.3), beri tahu IT bila terlihat seperti galat sistem (pesan merah, halaman kosong, data bocor). Hentikan & segera panggil IT bila Anda melihat data tenant lain, password tampil di layar/ekspor, atau aksi menyentuh ONT di luar daftar uji.
  5. 12.00–13.00: O13–O29 (Zero-Touch, Preset, RBAC, audit, impor/ekspor, diagnostics, MFA, laporan SaaS, impersonate, paket, portal, vendor generik).
  6. 13.00: G1 (bersama Network) & G2 (simulasi keluhan pelanggan) — catat waktu yang dibutuhkan.

5.3 Setelah UAT

  • Serahkan lembar hasil Bagian B/C (§8, §9) dan templat temuan ke IT.
  • Masukan kemudahan pakai (penting): tulis 3 hal paling membingungkan, 3 hal paling membantu, dan 3 hal yang masih kurang untuk pekerjaan harian.
  • Ganti password akun uji (atau minta IT menonaktifkannya).

10 Yang sudah diketahui belum lengkap (bukan temuan baru)

Daftar ini ditulis jujur agar waktu UAT tidak terbuang. Bila menemui salah satunya, cukup beri tanda "diketahui" di lembar hasil; tetap catat bila dampaknya lebih besar dari yang dijelaskan.

BatasanDampak & cara menyikapi
Belum pernah diuji pada ONT fisikInilah gunanya UAT. Perilaku per-firmware bisa berbeda; catat vendor, model, firmware persis.
ACS tidak mengatur OLTRegistrasi ONT, VLAN, profil bandwidth, level optik di OLT: tetap di sistem OLT. Modul OLT Controller dijadwalkan setelah UAT.
CWMP via HTTP (acsd tanpa TLS)Kredensial Inform lewat Basic Auth tanpa enkripsi bila tanpa reverse proxy TLS. OK di LAN uji tertutup. Overlay TLS (Caddy) tersedia dan teruji fungsional, belum dengan ONT fisik.
Semua nilai SetParameterValues bertipe xsd:stringFirmware ketat bisa menolak boolean/angka dengan Fault 9006/9007. Catat parameter+model+firmware.
Parameter per-band belum dipetakan; optik terbatasKatalog bawaan: radio utama instance 1 (SSID, passphrase), PPPoE, info perangkat, diagnostics, dan optik TR-181 standar + sebagian path vendor. SSID 2,4/5 GHz terpisah, IP WAN, dan optik vendor lain: path beda tiap vendor — catat path asli bila ditemukan.
Fault 9005 (parameter tidak ada)Tidak di-retry (memang disengaja). Path mapping tidak cocok dengan firmware itu.
Rate limit CWMP 5 req/dtk per IP (bawaan)Banyak ONT di balik satu IP publik bisa kena HTTP 429 saat boot bersamaan; ONT mencoba lagi sendiri. Dapat dinaikkan dengan ACS_CWMP_RATE_LIMIT.
Connection Request ke ONT di balik CGNATACS mencoba HTTP lalu fallback UDP Connection Request (TR-069 Annex G, HMAC-SHA1; bukan STUN) — teruji hanya terhadap penerima uji, belum ONT nyata. 502 = tidak terjangkau; task tetap menunggu Inform berikutnya.
Diagnostics bergantung dukungan ONTPing/Traceroute sudah berjalan end-to-end terhadap simulator; pada ONT nyata hasilnya bergantung dukungan IPPingDiagnostics/TraceRouteDiagnostics firmware. Gagal dengan fault = catat model+firmware (O21).
Realtime (WebSocket)Sudah tersambung (indikator "Live"; task/perangkat ter-refresh seketika). Bila indikator tidak "Live", periksa ACS_CORS_ALLOW_ORIGINS (origin Console harus persis sama) dan firewall port API. Data tetap ter-refresh berkala sebagai cadangan.
Daftar vendor/OUI tambahan adalah data awalSejak 17 Okt katalog berisi 33 vendor dan ±4.300 OUI dari registry IEEE plus mapping standar (vendor GENERIC). Semuanya belum diuji pada ONT nyata; OUI di DeviceId bisa berbeda dari OUI MAC. Path optik TR-098 per vendor sengaja belum dipetakan (O21 & polling optik hanya memakai path standar TR-181).
Pendaftaran tenant mandiri mati secara bawaanTidak termasuk UAT ini (butuh SMTP & keputusan bisnis). Halaman Syarat/Privasi di Console adalah draf yang belum ditinjau hukum.
Sesi berstatus TIMEOUTNormal: sesi tanpa POST penutup ditutup otomatis setelah 15 menit.
Email ke domain uji (*.local, example.*) tidak dikirimDisengaja. Pakai alamat email nyata untuk uji email.
Firmware upgrade belum pernah diuji ke ONT fisikTidak termasuk UAT ini (§1).
Nilai rahasia di Preset/ProfilDienkripsi AES-GCM di database untuk nama parameter sensitif (password/psk/secret/token/key) dan disamarkan di API untuk non-admin; ekspor CSV mengosongkannya. Baris lama dienkripsi dengan /app/seal-secrets (IT). Nilai yang dilaporkan ONT (tab Parameter) tetap plaintext di DB, disamarkan di API untuk non-admin. Tetap gunakan kredensial uji.
SSO OIDCTeruji terhadap IdP tiruan (tanda tangan, nonce, issuer/audience, pemetaan akun lewat email), belum terhadap IdP organisasi Anda. Login SSO tidak menambah MFA lokal (andalkan MFA di IdP). Tidak ada pendaftaran otomatis: akun harus dibuat admin dengan email yang sama.
KapasitasUji beban lab (minimal Inform, satu instance, laptop Docker): ~550–620 sesi/dtk tanpa galat, p95 ≈ 99 ms pada 50 koneksi. Bukan jaminan kapasitas pada ONT nyata (Inform nyata lebih berat). Mode multi-instance (ACS_HA) tersedia tetapi di luar cakupan UAT.

Usulan kriteria GO untuk lanjut ke pilot terbatas
  • Minimal 1 ONT pada ≥ 1 vendor lulus: N1, N2, N3, N6, O5, O10, O11, G1.
  • Tidak ada S1 terbuka. S2 boleh ada bila punya jalan pintas & tiket perbaikan.
